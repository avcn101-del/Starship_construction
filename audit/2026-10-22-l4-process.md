**F3 [PG]** The three locks fall in the **same minute as the build and scenario commits** (06:02/07:30/09:43). The history can show the order of commits, not what happened before them. The only evidence of the engineer's pre-lock runs is prose: reviewer N3 "the PR body says each new scenario was run once before the lock and the engineer saw the verdicts. B10's hand-worked literal and B15's setup were changed after that run"; #267 (10) "the engineer ran each scenario once before the lock, saw the verdicts, then corrected B10's literal (its own rounding) and B15's setup … accepted … and the rule stays 'hide the results'". For L4a and the fix round the record says nothing about a pre-lock run. **Resolution:** require each engineer's PR body to state the number of pre-lock runs and what was edited after them (a fixed section), so a reviewer can check it, instead of finding it by reading prose.

**F4 [Q / PG] Is 'run only for crashes, hide results' (`.claude/agents/engineer.md:18`) kept, and worth keeping as written?** The rule cannot be enforced: a run prints a verdict, and the engineer in L4b saw them and then edited B10's literal. #267 (10) accepts the case because the blind checker re-derived both values independently, i.e. **the protection that held is the blind checker, not the rule**. Cost-benefit: a pre-lock run that sees PASS/FAIL cannot be unseen; the rule's real content is "no tuning to a verdict". Resolution (for the owner, since `CLAUDE.md` says criteria are locked before running): rewrite as "a pre-lock run may be done for crashes and setup errors; any edit made after it is listed in the PR body with the reason; a hand-worked literal is derived from the formula and not from a printed value", and keep the blind checker mandatory for kernel physics (#241 (4)).
